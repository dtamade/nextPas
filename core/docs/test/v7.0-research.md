## 1. Test Cache（测试缓存）

### 1.1 Go 机制深度分析

**缓存键生成** (`cmd/go/internal/test/test.go`):
1. **Test ID** = hash(test binary + test function name + `-_test.gotest` flag set)
2. **Input ID** = hash(test log): 测试运行期间所有 `os.Open`, `os.Getenv`, `os.Stat`, `os.Chdir` 调用
3. **Final Key** = `testAndInputKey(testID, testInputsID)`

**关键细节**:
- `testlog` 包通过 `atomic.Value` 挂钩到 `os.Getenv`, `os.Open`, `os.Stat`, `os.Chdir`
- 测试结束后 `StopTestLog()` flush 到 writer，cmd/go 解析这个 log 提取所有 file/env 依赖
- 缓存过期通过写入时间戳到 `$GOCACHE/<hash1>/<hash2>` 目录实现
- `go clean -testcache` 仅写入一个时间戳，不删文件（惰性过期）

**缓存粒度**: 每个 test function 独立缓存（不是 suite 级别）

**禁用条件**:
- `-count=1` 或 `-count > 1`
- 测试在 module root 外
- 使用了 `-bench` 或 `-fuzz`

### 1.2 Pascal 设计方案

**核心差异**: FPC 无法像 Go 那样在 runtime 拦截 `os.Open`/`os.Getenv`。需要用户显式声明依赖。

**方案 A: 保守方案（推荐）** — hash 源文件 + 编译器 + 配置

```pascal
type
  TCacheEntry = record
    Status  : TTestStatus;
    Message : string;
    Duration: Int64;
    Time    : Int64;  { Unix timestamp }
  end;

  TTestCache = record
    CacheDir: string;  { 默认 .nextpas/test-cache/ }

    function  ComputeKey(const ASources: array of string;
                const ACompilerVersion: string;
                const AConfig: TTestConfig): string;
    function  Get(const AKey: string; ATestName: string;
                out AEntry: TCacheEntry): Boolean;
    procedure Put(const AKey: string; ATestName: string;
                const AEntry: TCacheEntry);
    procedure Clean(AmaxAgeDays: Integer = 30);
    procedure Invalidate;
  end;
```

**缓存键**:
- 源文件内容 hash (SHA256 of `*.pas` in src + test dir)
- FPC 版本 (`fpc -iV`)
- 编译标志 (FPC_FLAGS)
- 测试配置 (filter, shuffle, timeout, short mode, verbose)

**CLI**:
- `--cache` 启用
- `--no-cache` 禁用
- `--cache-clean` 清理
- `--cache-dir=<dir>` 指定目录

**实现量**: ~300 行

### 1.3 价值评估

| 场景 | 价值 | 说明 |
|------|------|------|
| CI 无变更重跑 | 高 | 秒级完成 |
| 本地开发迭代 | 中 | FPC 编译本身秒级 |
| 大型 suite | 中 | 500+ 测试套件 |

**结论**: 中等价值。FPC 编译速度本身很快（~1-2s），cache 主要收益在 CI 场景。

## 2. Fuzzing（模糊测试）

### 2.1 Go Fuzzing 架构

从 `testing/internal/testdeps/deps.go` 可见:

```go
func (TestDeps) CoordinateFuzzing(
    timeout time.Duration, limit int64,
    minimizeTimeout time.Duration, minimizeLimit int64,
    parallel int, seed []fuzz.CorpusEntry,
    types []reflect.Type, corpusDir, cacheDir string) error
```

**核心特性**:
- **Coverage-guided**: 内置覆盖率采集 (`ResetCoverage`/`SnapshotCoverage`)
- **Seed corpus**: `f.Add(...)` 注入种子
- **Mutation**: 内置变异引擎（字节翻转、插入、删除、整数边界）
- **Shrinking**: 发现 crash 后自动最小化输入
- **Worker 进程**: fuzzing 在独立进程运行，避免影响主测试
- **Corpus 存储**: `testdata/fuzz/<FuzzFunc>/` 目录

### 2.2 Rust 方案对比

| 方案 | 覆盖率引导 | 最小化 | 依赖 |
|------|----------|--------|------|
| cargo-fuzz (libFuzzer) | ✅ | ✅ | LLVM |
| proptest | ❌ | ✅ | 纯 Rust |
| quickcheck | ❌ | ✅ | 纯 Rust |

### 2.3 Pascal 设计方案

**Phase 1: Mutation-only（纯变异，无覆盖率）**

```pascal
type
  TFuzzResult = record
    Passed  : Boolean;
    Iters   : Int64;
    CrashInput: TBytes;      { 最小化后的 crash 输入 }
    CrashMsg  : string;
    ElapsedMs : Int64;
  end;

  TFuzzProc = procedure(const AData: TBytes);
  TFuzzStrProc = procedure(const AData: string);
  TFuzzIntProc = procedure(const AData: Int64);

  TFuzzTarget = record
    Name: string;
    Seeds: specialize TArray<TBytes>;

    procedure AddSeed(const AData: TBytes);
    procedure AddSeedStr(const AData: string);
    procedure AddSeedInt(AValue: Int64);
    function  Run(AProc: TFuzzProc;
                ADurationMs: Integer = 5000): TFuzzResult;
  end;
```

**变异策略** (mutation-only):
- 字节翻转 (bit flip)
- 字节替换 (random byte)
- 块插入 (insert random block)
- 块删除 (delete random block)
- 整数边界 (0, 1, -1, MaxInt, MinInt)

**Shrinking**: 
- 二分法: 依次移除前半/后半，看是否仍 crash
- 字节删除: 逐字节删除，保留最小 crash 输入

**CLI**:
- `--fuzz[=pattern]` 启用 fuzzing
- `--fuzztime=Nms` 每个 target 时间限制 (默认 5s)
- `--fuzz-seed=N` 随机种子 (可复现)

**实现量**: ~500 行 (mutation + shrinking + corpus management)

**Phase 2: Coverage-guided（未来，需编译器支持）**
- 需要 FPC `-fsanitize-coverage` 或 LLVM 插桩
- 复杂度高，建议 v8.0+

### 2.4 价值评估

| 场景 | 价值 | 说明 |
|------|------|------|
| Parser 边界 bug | 高 | 字节流输入天然适合 fuzz |
| 加解密模块 | 高 | 任意输入不应 crash |
| 序列化/反序列化 | 高 | JSON/TOML/YAML 解析器 |
| 一般业务逻辑 | 中 | 需要精心设计 seed |

**结论**: 高价值但实现复杂。Phase 1 (mutation-only) 已能发现大部分 crash bug。

## 3. Parallel Opt-in（并行控制）

### 3.1 Go 机制

```go
func TestA(t *testing.T) {
    t.Parallel()  // 标记为并行
}

func TestB(t *testing.T) {
    // 不调用 = 串行
}
```

**执行模型**:
1. 所有非 `t.Parallel()` 测试先串行执行
2. 然后所有 `t.Parallel()` 测试并行执行
3. 非并行测试先跑完是隐式 barrier

### 3.2 Pascal 设计方案

**最小方案**: Sequential 标记

```pascal
// TTestEntry 新增字段
Sequential: Boolean;  { true = 在并行模式下串行执行 }

// TTestSuite 新增方法
procedure TestSeq(const AName: string; AProc: TTestProc);
procedure TestSeq(const AName: string; AProc: TTestClosure);
```

**执行模型** (Go 风格):
```
RunParallel:
  Phase 1: 串行执行所有 Sequential=true 的测试（逐个）
  Phase 2: 并行执行所有 Sequential=false 的测试（batch dispatch）
```

**使用示例**:
```pascal
Suite := TTestSuite.Create('mixed');
Suite.Test('fast_a', @TestA);           { 并行 }
Suite.Test('fast_b', @TestB);           { 并行 }
Suite.TestSeq('shared_db', @TestDB);    { 串行 — 有共享状态 }
Suite.Test('fast_c', @TestC);           { 并行 }
```

**实现量**: ~150 行

### 3.3 价值评估

| 场景 | 价值 | 说明 |
|------|------|------|
| 共享 DB/文件测试 | 高 | 避免 flaky |
| 混合 suite | 高 | 有些测试天然适合并行，有些不是 |
| 纯计算测试 | 低 | 本身就安全并行 |

**结论**: 高价值、低实现成本。应优先实施。

## 5. 附录：Go testlog 机制细节

Go 通过 `internal/testlog` 包挂钩 `os` 包的 `Getenv`/`Open`/`Stat`/`Chdir`:

```go
// internal/testlog/log.go
type Interface interface {
    Getenv(key string)
    Stat(file string)
    Open(file string)
    Chdir(dir string)
}
```

cmd/go 收集这些调用作为 test 的"输入列表"，用于缓存键计算。

**Pascal 启示**: 我们无法在 FPC runtime 拦截文件操作。保守方案是 hash 所有源文件（包括测试本身和被测模块），不需要精确的文件依赖追踪。
