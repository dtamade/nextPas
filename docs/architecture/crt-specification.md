# nextPas CRT 规范

用这份规范定义 nextPas 第一阶段 CRT 的边界。CRT 在兼容性矩阵里属于范围内
硬目标，但它不能继续被写成泛化 RTL 的附注，因为控制台导向行为只有在单独成文、
单独测试时，才真正可管理。

## 为什么 CRT 需要独立规范

nextPas 第一阶段同时保留 RTL 行为和 CRT 行为，但这两类行为的验证重点不同：

- `rtl/core/` 关注 `System`、文件处理与其他核心运行时服务。
- `rtl/crt/` 关注控制台会话、交互式文本环境和终端相关的可观察行为。
- `tests/rtl/` 与 `tests/crt/` 必须继续保持分桶，而不是共享一份模糊的运行时说明。

把 CRT 单独写出来，不是为了扩大范围，而是为了避免控制台行为在后续实现中失去
边界、失去证据、失去回归归属。

## 第一阶段中的 CRT 指什么

第一阶段的 CRT 只覆盖 Linux x86_64 基线与 smoke 路径需要的控制台行为，
并且要求这些行为保持显式、可单独测试、可失败留证。

| CRT 行为层 | 第一阶段要求 |
|------------|--------------|
| 文本控制台输出 | 保持基线样例依赖的文本输出路径与可观察结果 |
| 控制台状态管理 | 对屏幕、光标、文本模式等状态变化保持显式边界，而不是散落在其他运行时代码中 |
| 交互式输入路径 | 对键盘或其他控制台输入相关行为保持可测试入口，并允许在不支持场景下确定性失败 |
| 会话级清理 | 让控制台状态恢复、退出行为与失败路径可以被回放和诊断 |

这里的重点是“把控制台行为定义清楚”，而不是承诺第一阶段就完成一套完整的终端
抽象层。

## `rtl/crt/` 与 `rtl/core/` 的分工

CRT 与核心 RTL 的分工必须稳定，否则测试和目录都会失去意义。

| 边界 | 归属 |
|------|------|
| 程序基础运行时、`System` 基线、文件处理 | `rtl/core/` |
| 控制台文本界面、交互会话、终端状态管理 | `rtl/crt/` |
| 无法判断归属的共享辅助逻辑 | 先按调用方责任拆清，再决定放入 `rtl/core/` 还是 `rtl/crt/` |

这也意味着 CRT 不能反向侵入 `rtl/core/`，把控制台假设变成所有运行时代码都必须
继承的隐式前提。

## CRT 必须对应独立测试证据

第一阶段的 CRT 规范必须直接映射到验证结构：

- `tests/crt/` 负责控制台行为断言。
- `tests/harness/` 负责组织这些断言的执行与留证。
- smoke 样例只覆盖当前基线最小需要的控制台路径，不自动等于完整 CRT 覆盖。
- `tests/regression/` 用于承接已经确认过的控制台回归样例。

如果某个控制台问题被修复后无法明确归档到 `tests/crt/` 或 `tests/regression/`，
说明这项修复还没有沉淀成 nextPas 的正式 CRT 资产。

## CRT 与阶段推进的关系

- `stage0`：先把控制台边界写清楚，并由 FreePascal 托管的驱动路径来验证。
- `stage1`：nextPas 可以接管更多控制台实现细节，但不能改变已文档化的控制台范围。
- `stage2`：只有当更深层的运行时与宿主关系已经被证明稳定后，才允许调查更强的
  自托管路径。

阶段推进可以增加实现所有权，但不应该让 CRT 再次退回“散落在 RTL 各处的
隐式行为集合”。

## 第一阶段非目标

这份 CRT 规范刻意排除以下内容：

- 不承诺一次性覆盖完整的历史 CRT 行为面。
- 不引入面向 Windows 或 macOS 的控制台分支设计。
- 不把图形、GUI 或全屏 TUI 框架混入 CRT 范围。
- 不把 CRT 文档降格为泛化 RTL 文案中的一小段说明。
- 不把 CRT 二进制接口稳定性写成当前 gate，`ABI compatibility is deferred`。

第一阶段要得到的是“可验证的控制台规范”，而不是一个难以回归的终端愿景清单。
