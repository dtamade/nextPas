# nextPas 兼容性矩阵

使用这份矩阵来决定 nextPas 在第一阶段必须保留什么，以及哪些内容要继续延后。
目标不是用一句模糊的“全面兼容”把一切遮住，而是把兼容层级说清楚、
把范围写清楚，并让权衡具备可验证性。

## 把兼容性承诺写清楚

| 层级 | 第一阶段状态 | nextPas 必须保留什么 |
|------|--------------|----------------------|
| Source syntax | 硬目标 | 解析并接受基线套件和 smoke 路径所需的 FreePascal 源码形式 |
| Core semantics | 硬目标 | 保持影响正确性、控制流、类型和可观察结果的语言行为 |
| 单元/模块行为 | 硬目标 | 保持 unit 命名、查找和依赖行为，足以支撑从冻结 FPC 参考树进行分阶段迁移 |
| RTL 行为 | 硬目标 | 保持基线套件依赖的运行时行为，尤其是 `System`、文件处理和其他核心服务 |
| CRT 行为 | 范围内硬目标 | 让控制台导向的运行时行为保持显式、可单独测试，并且与第一阶段 smoke 路径兼容 |
| 包兼容分层 | 分阶段推进 | 先完成核心运行时基线，再按明确层级扩展包，而不是一次性承诺整个 FPC 包生态 |
| 诊断预期 | 硬目标 | 即使还没有做到逐字节一致，也要提供确定性的失败分类、稳定的退出行为和便于留证的输出 |
| ABI / binary compatibility | 延后 | ABI compatibility is deferred |

## 用包分层，而不是一句笼统承诺

包兼容必须分层，因为 FPC 的 `packages/` 树既宽广又异构。

| 分层 | 第一阶段预期 |
|------|--------------|
| 第 0 层 | 仅覆盖核心编译器、RTL 和 CRT 基线 |
| 第 1 层 | 覆盖直接支撑 `stage0` 与验证路径的精选包 |
| 第 2 层 | 在基线稳定后再逐步扩展到更广的包生态 |

这样做可以让第一阶段保持诚实。nextPas 可以对兼容性保持强承诺，但不必假装
每个 FPC 包都要在第一阶段一开始就成为硬要求。

## 让延后项保持可见

“延后”不等于“忽略”。它表示项目明确选择不把这件事设为第一阶段 gate。

- ABI compatibility is deferred，直到编译器和运行时有足够证据来定义稳定的
  二进制兼容约束。
- Delphi 兼容不是第一阶段目标。
- 在与 FPC 兼容的基线还在建立时，新语法工作不在范围内。
