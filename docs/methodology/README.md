# 开发方法论

## 核心原则

**先规范后代码，先计划后执行。**

所有代码变更必须经过严格的四步流程，不允许"先写代码再补文档"。

---

## 四步流程

### Step 1: Plan（规划）

**输入**：需求或问题描述
**输出**：Plan 文档（`.claude/plans/`）+ 契约更新

必须完成：
- [ ] 明确变更范围（哪些文件、哪些公开 API）
- [ ] 识别影响面（哪些模块/测试会受影响）
- [ ] 更新或创建代码契约文档（`CONTRACT.md`）
- [ ] 评估风险（是否有破坏性变更、是否需要迁移）

**门禁**：Plan 文档存在且契约已更新，才能进入 Implement。

### Step 2: Implement（实现）

**输入**：Plan 文档
**输出**：可编译的代码 + 测试

必须完成：
- [ ] 按契约写代码，不偏离 Plan
- [ ] 每个 commit 必须通过编译
- [ ] 新增/修改的公开 API 必须有文档注释
- [ ] 新增代码必须有对应测试

**门禁**：代码编译通过，测试不回归。

### Step 3: Review（审查）

**输入**：代码变更 + 契约文档
**输出**：审查报告

必须完成：
- [ ] 对照契约逐项检查：接口一致性
- [ ] 检查不变量是否仍然成立
- [ ] 检查错误处理路径是否完整
- [ ] 检查线程安全声明是否正确
- [ ] 检查内存管理是否符合所有权模型
- [ ] 检查测试覆盖是否完整

**门禁**：审查报告 0 个 P0/P1 问题。

### Step 4: Verify（验证）

**输入**：代码变更
**输出**：测试报告

必须完成：
- [ ] 运行完整测试套件（不是 smoke test）
- [ ] 确认 0 失败
- [ ] 确认无内存泄漏（heaptrc）
- [ ] 确认无回归

**门禁**：全量测试 0 失败，才能合并。

## 契约文档要求

每个模块必须有 `CONTRACT.md`，包含六项内容：

| 项 | 描述 | 必须 |
|----|------|------|
| 接口契约 | 公开类型、函数、参数约束、返回值语义 | ✅ |
| 不变量 | 必须始终为真的条件（INV-1, INV-2, ...） | ✅ |
| 错误处理 | 异常层级、错误码、graceful degradation | ✅ |
| 线程安全 | 并发模型、锁策略、无锁保证 | ✅ |
| 内存管理 | 所有权模型、生命周期、leak-free 保证 | ✅ |
| 测试覆盖 | 必须覆盖的场景清单 + 测试文件映射 | ✅ |

契约文档位置：`core/docs/<module>/CONTRACT.md`

## Worktree 纪律

### 核心规则

1. **一个功能/模块一个 worktree**：不允许在 main 上直接开发
2. **main 只用于 landing**：合并已完成的功能线
3. **worktree 合并前必须通过四步流程**

### Worktree 目录结构

```
.worktrees/
  mem/          ← mem 模块开发
  compiler/     ← 编译器开发
  test/         ← 测试框架开发
  bench/        ← 基准测试
  gpu-window/   ← GPU 窗口开发
```

### 合并流程

1. worktree 上完成四步流程
2. 运行 `make hygiene` 确认无构建产物
3. 运行 `git diff --check` 确认无冲突标记
4. 合并到 main
5. 清理 worktree（可选保留）

---

## 门禁脚本

### `scripts/mem-contract-check.sh`

检查 mem 模块的契约完整性：
- 新增/修改的公开类型是否有契约文档
- 新增/修改的公开函数是否有接口契约
- 不变量列表是否与代码同步
- 测试覆盖清单是否更新

### 集成到 `make verify`

```bash
make verify  # 编译 + 测试 + 契约检查
```

---

## 违规处理

| 违规类型 | 处理 |
|----------|------|
| 代码变更无契约更新 | 阻塞合并 |
| 新增公开 API 无文档注释 | 阻塞合并 |
| 测试覆盖不完整 | 阻塞合并 |
| 在 main 上直接开发 | 警告 + 迁移到 worktree |
| worktree 合并前未走四步流程 | 阻塞合并 |
