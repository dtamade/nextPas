# nextPas 第一阶段 packages 推进计划

- 状态：规划中
- 日期：2026-03-21
- 范围：phase1 `packages/` 分阶段推进设计

## 把这份文档当作 `packages` 的执行级入口

这份文档承接 `docs/architecture/packages-specification.md`，把已经冻结的
`packages/` 稳定边界进一步转成可执行的推进设计。

它不改写 `packages-specification.md`、`compatibility-matrix.md` 或 ADR 中已经冻结的
范围，而是回答更具体的问题：

- phase1 里先碰哪些包族，为什么是它们
- 哪些包族继续明确延后
- 包兼容要沿着什么波次推进
- 每一波进入实现前必须具备哪些验证与留证条件

## 当前前提

这份计划建立在以下前提之上：

- 第一阶段唯一宿主与目标仍是 Linux x86_64。
- FreePascal 继续作为 `stage0` 宿主工具链。
- `packages/` 仍然服从 `compiler`、`rtl`、`crt`、`build`、`tests` 与发行布局这些
  已冻结边界。
- phase1 的核心任务仍是建立可验证基线，不是追求整个 FPC package universe。

如果这些前提变化，这份计划必须被重写，而不是悄悄扩大解释范围。

## 用这三条筛选规则决定谁能先进入 phase1

任何包族想进入 phase1 的优先波次，至少要同时满足：

1. 它直接支撑 `stage0`、`harness`、smoke/regression 路径，或者能明显降低后续
   迁移的不确定性。
2. 它可以在 Linux x86_64 上以可解释的方式验证，不依赖未文档化的 GUI、
   平台专用 ABI、外部服务或庞大系统库前提。
3. 它不会反向逼迫 `compiler`、`rtl`、`crt` 或目标平台规格扩大当前承诺。

不满足这三条的包，不是“以后再说”的模糊区域，而是明确延后。

## 先按包族推进，而不是先按完整包名清单推进

FPC `packages/` 顶层同时包含 `fcl-*`、`rtl-*`、数据库、网络、GUI、多媒体、
平台专用 units、外部库绑定和工具链扩展。对 nextPas 来说，先把这些包按推进特征分组，
比先复制一份很长的包名单更有决策价值。

这份计划采用三波次结构：

| 波次    | 包族                                             | 候选样本                                                                       | 为什么先/后                                                                       | 进入 gate                                                                    |
| ------- | ------------------------------------------------ | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 波次 P1 | 纯 Pascal、低外部依赖、语言/运行时相邻的基础包族 | `rtl-generics`、`rtl-objpas`、`fcl-base`、`fcl-process`、`fcl-hash`、`regexpr` | 最容易在 Linux x86_64 上做可重复验证，也最适合作为 core baseline 之外的第一层扩展 | 需要明确依赖边界、最小 smoke 样例、可映射到 `units/linux-x86_64/` 的安装语义 |
| 波次 P2 | 文本、数据与测试支持包族                         | `fcl-json`、`fcl-md`、`paszlib`、`fcl-fpcunit`、`fcl-passrc`、`fcl-syntax`     | 能增强验证、样例和迁移能力，但仍应尽量避免 GUI/系统库重依赖                       | 需要在现有 `harness` 路径里找到清晰挂点，并写清包与 `tests` 的关系           |
| 波次 P3 | 服务、网络与数据访问包族                         | `fcl-net`、`fcl-web`、`fcl-db`、`sqlite`、`postgres`、`mysql`、`odbc`          | 价值高，但外部服务、协议或系统依赖更多，不适合作为第一波 packages 基线            | 只有在 P1/P2 稳定后，且有明确依赖模型、测试环境和失败留证策略时才允许开始    |

这里的“候选样本”是用来定义包族，不是承诺这些包会一次性全部落地。

## 这些包族在 phase1 里继续显式延后

以下几类包先不进入 phase1 packages 优先波次：

- GUI、窗口系统和多媒体绑定：如 `gtk*`、`fpgtk`、`x11`、`opengl`、`opengles`、
  `sdl`、`cairo`、`gstreamer`、`openal`
- 强外部库绑定：如 `libcurl`、`openssl`、`libxml`、`libpng`、`fftw`、`libusb`
- 平台专用 units：如 `os2units`、`qlunits`、`winceunits`、`winunits-*`、`univint`
- 工具链与生态对等类扩展：如 `fppkg`、`ide`、`vcl-compat`

这些包不是“不重要”，而是当前不应该先于 core baseline 和低依赖包族进入 gate。

## 每一波进入实现前，都要先补这四类设计资产

包族一旦从“候选”进入实现，必须先具备：

| 资产       | 要求                                                                              |
| ---------- | --------------------------------------------------------------------------------- |
| 所有权说明 | 在 `packages/` 下为目标包族写清 README/边界说明，不把上游目录直接原样搬进 nextPas |
| 依赖声明   | 写清是否纯 Pascal、是否依赖 Linux 用户态库、是否要求外部服务或额外工具            |
| 验证入口   | 明确复用哪类现有验证路径：`compiler-pass`、`rtl`、`regression` 或 smoke 样例      |
| 发行落点   | 说明安装结果如何进入 `units/linux-x86_64/`，共享文档/样例如何进入 `share/`        |

如果这四类资产缺一，就还停留在规划阶段，不应该宣布进入实现。

## 先复用现有验证结构，不把 `tests/packages/` 当成前提

phase1 当前不把单独的 `tests/packages/` 测试桶设为前提。包兼容工作先按行为复用已有结构：

- 编译可达性或 unit 查找行为，优先落到 `compiler-pass` / `compiler-fail`
- 运行时行为，优先落到 `rtl` / `regression`
- 需要固定失败表面的场景，优先落到 `diagnostics`
- 标准演示路径继续优先使用 smoke 样例

只有当 P1 和 P2 已经证明“按行为分桶”不足以表达 packages 风险时，才讨论是否新增
专门的 packages 测试桶。

## 这份计划如何和现有 phase1 主线对齐

这份计划不替代 `docs/plans/2026-03-20-nextpas-phase1-bootstrap-plan.md`，也不改变
其中 6-12 号任务的执行顺序。它的作用是给 phase1 后续的 packages 工作一条受控入口：

- 在仓库骨架、`harness`、`stage0` 驱动、目标规格和发行布局收口后，packages 才允许
  按这份计划进入下一轮设计或实现。
- 如果当前主线任务暴露出新的 Linux x86_64、`stage0` 或发行布局限制，这份计划应先
  回收 packages 波次承诺，而不是让 packages 反向扩大主线。

换句话说，这是一份“后续 packages 怎么进场”的计划，不是“现在切换主线”的命令。

## 首轮验收要看什么

当后续有人基于这份计划继续推进时，至少要能回答这些问题：

- 这个包族为什么属于 P1、P2 或 P3，而不是更早或更晚？
- 它是否继续满足 Linux x86_64、FreePascal `stage0` 和现有发行布局约束？
- 它要复用哪个现有测试分桶，为什么？
- 它有没有引入新的外部库、服务或平台前提；如果有，为什么仍应进入当前波次？

如果答不清，就说明它还没准备好进入实现。

## 非目标

- 不把完整 FPC `packages/` 树写成 phase1 默认交付物。
- 不把 GUI、多媒体、平台专用 units 或大规模外部绑定混进首批波次。
- 不在当前阶段承诺包管理器、生态工具链对等或 ABI 稳定。
- 不让 `packages` 推进反向改写 `compiler`、`rtl`、`crt`、目标平台或发行布局的稳定边界。
