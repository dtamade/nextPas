# nextPas 迭代推进工作模式

- 状态：采用中
- 日期：2026-03-24
- 范围：nextPas 仓库中的人机协作推进节奏

## 用这份文档结束“碎片推进”

这份文档解决一个很具体的问题：工作一直在发生，但用户很难感到项目真的往前走了一块。

当前仓库已经有主计划、实施计划、`support` 进度日志、`.sisyphus/evidence/`，以及临时
`task_plan.md` / `findings.md` / `progress.md`。缺的不是更多计划文件，而是一套明确的
推进节奏，保证这些文件服务同一批交付，而不是把一次推进拆成许多几乎感知不到的小碎片。

这份模式不改写 ADR、架构规范或 phase1 任务边界。它只规定一件事：后续怎么推进，才能让
每一轮都有明确产出、边界、验收和停点。

## 先看三种模式，再确定推荐模式

### 模式 A：微步推进模式

做法是把工作拆成非常小的单元，一次只动一点，然后频繁回报。

优点：

- 风险低
- 每一步都容易解释

问题：

- 用户感受到的是“有动作”，不是“有交付”
- 很容易出现只更新计划、只补文档、只改一个小 helper 的碎片推进
- `继续` 会退化成催促下一小步，而不是推进下一批可见结果

这就是当前最让人疲惫的模式，不再推荐作为默认模式。

### 模式 B：批次推进模式

做法是把工作按“一个可感知结果”组织成批次。一个批次内部可以有多步，但对外只承诺一块完整交付。

优点：

- 用户每一轮都能看到一个完整结果
- 代码、文档、验证和证据会在同一批次里一起收口
- `继续` 的语义变成“继续当前批次或下一个批次”，不再是“再做一个小动作”

代价：

- 开始前必须把边界说清
- 中途不能随意切换主题

这是 nextPas 现在最合适的默认模式。

### 模式 C：长冲刺静默模式

做法是一次接很大目标，长时间自主执行，只在严重阻塞时打断。

优点：

- 理论上效率高
- 用户打断少

问题：

- 透明度太低
- 对当前 still-evolving 的 nextPas 设计来说，太容易在错误方向上跑太远
- 一旦方向错了，返工成本大

这个模式只适合边界已经非常稳定的大块实现，不适合作为当前默认。

## 默认采用模式 B：批次推进模式

从现在开始，nextPas 默认按“里程碑 > 批次 > 任务”的层级推进。

- 里程碑
  - 回答“现在在推进哪条主线”，例如 phase1 收口、diagnostics canonical snapshot、packages P1
- 批次
  - 回答“这一轮要交付什么完整结果”
- 任务
  - 回答“为了完成这个批次，内部要做哪些步骤”

真正的对外承诺单位是批次，不是任务。

也就是说，后续我不再把“补一个字段”“改一个 README 句子”“修一个 helper”单独当成一次推进结果，
除非它本身就是这个批次唯一且必要的交付。

## 每个批次开始前，先写批次契约

每一批开工前，先明确下面六件事：

1. `Batch Goal`
   - 这批结束后，仓库里新成立的能力是什么
2. `In Scope`
   - 这批明确要碰哪些目录和文档
3. `Out of Scope`
   - 这批明确不做什么，防止边做边扩
4. `Acceptance`
   - 哪些命令、哪些输出、哪些文档锚点算通过
5. `Evidence`
   - 哪些文件会写入 `.sisyphus/evidence/`
6. `Stop Conditions`
   - 什么情况必须停下来问用户

如果这六件事说不清，这一批就还没准备好开始。

## 每个批次内部，按这 6 步循环

### 1. 先锁边界，不先写散碎变更

先把当前批次对齐到现有 ADR、架构规范和活动计划。批次不能靠“先改一点再看”来定义自己。

### 2. 先做红灯检查

如果这批包含行为变化、命令输出变化、验证规则变化，先写或先运行一条失败验证，证明当前仓库还不满足这批目标。

### 3. 一次完成这一批的主体实现

实现期间可以分多步，但默认不把这些内部步骤拆成对外独立成果。

### 4. 在同一批里收口文档

只要这批改了公开边界、公开入口、计划状态或验证规则，相关文档必须在同一批内同步，不留到“下次继续”。

### 5. 跑 fresh verification

批次结束前必须重新运行完整的相关验证，而不是沿用上一次输出。

### 6. 交付一个完整批次包

对外汇报时只回答四件事：

- 这一批交付了什么
- 哪些验证新鲜通过
- 还剩什么真实风险
- 下一批建议做什么

## `继续` 在新模式里的含义要固定

从现在开始，`继续` 不再解释成“再做一点点”。

它只允许有两种含义：

1. 当前批次还没结束
   - 那就继续完成当前批次，直到交付或阻塞
2. 当前批次已经结束
   - 那就进入已经声明好的下一批，而不是临时挑一个小点继续摸

如果既没有当前批次，也没有下一批候选，我要先给出批次候选，再开始执行。

## 我会怎么汇报，避免“看起来一直在忙，但没有推进”

后续默认用下面这套汇报规则：

- 开始时
  - 给出 `Batch Goal`、范围、验收和我马上要做的第一步
- 中途
  - 只汇报已经确认的推进，不把猜想或未落地的计划伪装成结果
- 结束时
  - 交付完整批次包，不以“已经做了一部分”当作默认结束状态

我不会再把下面这些内容当成“这一轮已经算推进完了”：

- 只新增计划，没有落到代码或仓库实体
- 只补一个小注释，但没有让公开行为或边界更完整
- 只做局部验证，没有完成这一批承诺的收口

## 什么时候允许打断用户，什么时候不允许

默认不因为内部小步骤完成就打断用户。

只有这几类情况才需要停下来：

- 架构方向需要用户拍板
- 仓库出现真实阻塞，例如工具缺失、编译环境异常、磁盘或权限问题
- 连续多次尝试后仍无法把这一批推进到通过状态
- 继续推进会明显越过这批的边界

除此之外，我应该直接把这一批做完。

## 仓库里的文件各自怎么服务这套模式

- `docs/architecture/`
  - 继续定义稳定边界，不记录批次过程
- `docs/plans/...-plan.md`
  - 定义主线范围、批次顺序和验收口径
- `docs/plans/support/...-progress.md`
  - 记录每个批次的检查点、证据和下一批就绪状态
- `.sisyphus/evidence/`
  - 保留这一批的原始命令输出
- `task_plan.md` / `findings.md` / `progress.md`
  - 作为会话内工作文件，只服务当前批次拆解和恢复

这些文件不该再各自推进不同节奏。一个批次结束时，它们应该指向同一个结论。

## 每个批次的大小要受限

为了避免重新滑回“太小”或“太大”两种极端，默认采用下面的批次大小：

- 一批只服务一个主目标
- 一批最多带一个附属收口目标
  - 例如同步 README / 计划状态 / 证据
- 一批结束后，用户应该能用一句话说出“现在新多了什么”

如果一批做完之后，用户仍然很难说出仓库到底前进了哪一块，这一批就还是切得不对。

## nextPas 现在最适合的批次类型

结合仓库现状，后续优先采用这类批次，而不是继续散点推进：

- phase1 收口批
  - 例如 task 12 本地验证与 CI 收口
- 控制面完整化批
  - 例如让 `stage0` / `harness` / diagnostics snapshot 再往同一份结果契约靠近
- 垂直能力批
  - 例如 diagnostics canonical snapshot producer、packages P1 第一个真实包族入口
- 骨架落地批
  - 例如把某份已冻结规范真实落到仓库结构，而不是只补正文

不再推荐“只为了让仓库看起来有变化”的散点小修批。

## 采用后的默认协作协议

如果你接下来直接说：

```text
按批次推进：<目标>
```

我会默认执行下面的流程：

1. 先声明这一批的契约
2. 直接推进到这一批完成或明确阻塞
3. 同步代码、文档、验证和证据
4. 用一个完整批次包向你交付

如果你只说：

```text
继续
```

我会默认继续当前未完成批次；如果当前批次已经结束，我会先给出下一批候选，再进入执行。

## 当前推荐的第一批

按这套新模式，当前最合理的下一批不是再补一个小文档点，而是：

**批次目标：** 完成 phase1 task 12 的本地验证与 CI 收口，并把 phase1 主线推进到可正式结束的状态判断。

这批之所以应该优先做，是因为它能结束当前 phase1 长时间“已经差不多，但还没真正收口”的状态。

## 非目标

- 不把这份模式写成新的稳定架构规范
- 不引入额外的长期流程工具或复杂自动化框架
- 不要求每次都新建一整套 plan / research / progress 文件
- 不把批次推进解释成“更少验证”或“更少文档同步”

这份模式真正要做的事很简单：让后续每一轮推进都更像一次完整交付，而不是一串让人疲惫的“继续”。
